# 06 · 路线图、基准与风险

## 1. 三轨并行

| 轨 | 内容 | 人力 |
|----|------|------|
| **R 渲染** | dl → CPU 光栅 → GPU HAL → 瓦片缓存 → 合成线程 | 1.5 人 |
| **T 文本** | unicode → font → shape → edit | 1.5 人 |
| **U 框架** | base → layout → scene → style → 内置控件 → 平台 | 1 人 |
| （交叉） | devtools / CI / 示例应用 | 全组 20% |

假设 4 名资深工程师、无历史包袱、无外部依赖审批。**总工期 20 个月到 1.0**，其中文本轨是关键路径。

## 2. 阶段与出口标准

| 阶段 | 时间 | 交付 | 出口标准（gate） |
|------|------|------|------------------|
| **M0 骨架** | 1–2 月 | `base`（Result/容器/arena/字符串/数学）、CMake presets、自研测试框架、`dl` IR、CPU 光栅（rect/rrect/path）、golden runner、headless 构建 | `cmake --preset headless && ctest` 全绿；圆角矩形/圆/路径 golden 与手算参考图逐像素一致 |
| **M1 文本地基** | 2–4 月 | ucdgen、规范化、分段、换行、sfnt+glyf 解析、Tier A 整形、A8 字形 atlas | Unicode 官方 conformance 100%；拉丁整形 vs HarfBuzz ≥99.9% |
| **M2 布局与场景** | 3–5 月 | `LayoutUnit`、Row/Column/Stack/Scroll、InlineText 断行、信号系统、Element 树、record | 5k 节点布局 < 3 ms；1% 脏区布局 < 0.5 ms |
| **M3 GPU 起步** | 4–6 月 | Vulkan HAL、Tier 0/1 GPU 管线、atlas 上传、PSO 缓存、X11 窗口 + 输入 | 1080p@60 空转 < 2 ms CPU；首帧 < 150 ms |
| **M4 合成器** | 5–7 月 | 层树、512² 瓦片、picture cache、damage、present 定时、合成线程动画 | 全屏滚动静态内容时 GPU 时间 < 1 ms/帧；瓦片命中率 > 90% |
| **M5 编辑与 IME** | 6–8 月 | 编辑内核、IBus/Fcitx 桥、preedit 绘制、选区/撤销 | 中文输入实测与原生编辑框无法区分；20 万字文档输入无可感延迟 |
| **M6 Tier B 整形** | 6–9 月 | 阿拉伯/希伯来/天城文/孟加拉/泰米尔、CFF 解释器、变体字体 | Tier B 整形 ≥98% 一致；Noto 全脚本样本无崩溃 |
| **M7 Windows** | 8–10 月 | D3D12 后端、Win32 窗口、TSF、UIA、原生菜单、DnD、PMv2 DPI | 与 M4 同等性能指标；屏幕阅读器清单通过 |
| **M8 macOS** | 9–12 月 | Metal 后端、Cocoa、`NSTextInputClient`、`NSAccessibility`、120 Hz | ProMotion 下滚动 0 掉帧 |
| **M9 1.0-beta** | 12–15 月 | 20 个内置控件、主题系统、devtools、热重载、打包、3 个真实示例应用 | 3 个 app 在 Win/mac/Linux 跨平台 golden 一致；启动 < 100 ms |
| **M10 性能硬化** | 15–18 月 | 并行布局、瓦片预取、Tier 2 compute 覆盖、模糊/backdrop 优化、内存裁剪 | 全部基准达标（§3），无 P0 内存泄漏 |
| **M11 1.0** | 18–20 月 | 文档、示例、ABI 冻结、CI 矩阵（3 OS × 2 编译器 × ASan/UBSan/TSan） | 连续 30 天无回归；benchmark 无 >5% 退化 |
| **M12+ 扩张** | 20 月+ | Android/iOS/WASM、Tier C 脚本、PDF/SVG 导出、远程渲染 | 按市场反馈排优先级 |

## 3. 基准套件（可复现、可门禁）

`bench/` 下 6 个场景，全部能在 headless（CPU 光栅）与 GPU 两种后端跑，输出 JSON 结果供 CI 对比。

| # | 场景 | 度量 | 目标 |
|---|------|------|------|
| B1 | 5,000 行虚拟列表滚动（20 万字形） | 帧时间 P50/P99、掉帧数、整形缓存命中 | 120 Hz 下 0 掉帧，P99 < 8.3 ms |
| B2 | 2,000 个动画卡片（transform+opacity+阴影） | 帧时间、GPU 时间、瓦片复用率 | 144 Hz 下 0 掉帧 |
| B3 | 布局抖动：10k 节点、每帧 1% 脏区 | build/style/layout/record 分段 | UI 线程 < 2 ms P99 |
| B4 | 冷启动到首帧 + 二进制体积 + 峰值 RSS | 时间/字节 | < 100 ms / < 8 MB / < 120 MB |
| B5 | 玻璃拟态：30 层 backdrop-blur | 帧时间 | 60 Hz 达标 |
| B6 | 图表：10 万线段 + 5k 点 | 帧时间、Tier 2 覆盖率正确性 | 60 Hz，边缘与 CPU 参考差 ≤2% |

对比基线（在同一台机器上跑，不要引用别人的博客数字）：
Qt6 Widgets 等价场景、Qt Quick 等价场景、Flutter 3.x desktop 等价场景。**每个 PR 的 CI 只跑 B1/B3（快）；每晚跑全量。**

## 4. 关键决策记录（ADR）

| # | 决策 | 备选 | 理由 |
|---|------|------|------|
| A1 | 基线 C++20，`NQ_HAS_CXX23` 渐进 | 直接要求 C++23 | 目标平台工具链（gcc11/clang14/MSVC19.3）缺 `<expected>`/`<format>`；自研 `Result`/`fmt` 成本 < 1 周 |
| A2 | `-fno-exceptions -fno-rtti` | 用异常做错误处理 | 体积、无隐藏分配、ABI 稳定、与 C ABI 一致 |
| A3 | 零第三方运行时依赖 | 直接用 Skia/HarfBuzz/ICU | 许可证自由度、可静态链接、WASM/嵌入式、供应链审计；代价是文本工期（已计入） |
| A4 | 第三方仅作 CI oracle | 无对照 | 用权威实现做测试基准，不承担运行时风险；这是 A3 能成立的前提 |
| A5 | 布局定点 `LayoutUnit`（1/64 px） | f32/f64 布局（Flutter 用 f64） | 跨平台像素一致、无累积误差、golden 可逐像素比 |
| A6 | CPU 光栅器为像素真值 | GPU 为真值 | 无驱动差异、可 headless、可打印/远程复用 |
| A7 | 第一年只做 Vulkan + 手写 Metal/D3D12 shader | 自研跨后端着色器编译器 | shader 仅 ~20 个，编译器是另一年工程量 |
| A8 | picture cache 全自动 | 让用户手加 `RepaintBoundary` | 默认路径必须是快的路径，否则用户永远踩坑 |
| A9 | 不做 VDOM diff，信号直连 | 类 React 的 diff | 减少每帧工作量；结构变化才 diff |
| A10 | 无法实现的脚本降级并显式标注 | 静默错误 | 宁可"看得见的降级"，不要"看起来能用的错字" |
| A11 | 提供 `system_hb` 应急开关（默认关） | 完全没有回退 | 排障与客户救火通道，不进入默认产物 |

## 5. 风险登记

| 风险 | 概率 | 影响 | 缓解 | 触发后的动作 |
|------|------|------|------|-------------|
| 整形一致性达不到（复杂脚本） | 高 | 高 | 分级交付 + CI oracle + `system_hb` 开关 | 复杂脚本外挂可选后端，其余保持自研 |
| CFF/Type2 解释器与真实字体兼容 | 中 | 中 | 用 Noto 全家族 + fuzz + FreeType 对照 | 优先支持 CFF2/变体，CFF1 降级为轮廓提取失败时的兜底字体 |
| 自研 PNG/JPEG 解码安全漏洞 | 中 | 高 | libFuzzer 常驻、尺寸上限、可选子进程沙箱解码 | 关键客户可切系统解码 |
| GPU 驱动碎片化（尤其 Android/老 Intel） | 高 | 中 | Tier 3 兜底、设备黑名单、GLES 后端 | 按机型白名单降级 |
| 无障碍验收不过 | 中 | 高 | 每平台实测清单 + 早期介入（M5 起） | 延后该平台 1.0，桌面先行 |
| 布局缓存正确性（脏标记漏标导致错帧） | 中 | 高 | "校验模式"：debug 下每帧全量重算并比对缓存结果 | 关闭缓存分支修复，再加回归用例 |
| 工期（20 个月） | 中 | 高 | 阶段 gate + kill criteria | 见 §6 |
| 生态/控件数量不足 | 高 | 高 | 先做 20 个高质量控件 + 迁移指南；后续社区 | 提供 Qt/QML 迁移工具降低采用成本 |

## 6. kill criteria（诚实止损）

- **M1**：Unicode conformance < 95% 或拉丁整形一致率 < 98% → 重新评估自研整形，改为"自研 unicode/bidi/换行 + 外挂整形后端"。
- **M2**：5k 节点布局 > 6 ms → 布局架构回炉（缓存/fragment 设计），不进入 GPU 阶段。
- **M4**：120 Hz 滚动仍有 >1% 掉帧 → 暂停上层功能，重做瓦片/光栅调度。
- **M9**：3 个示例应用无法在 3 平台做到 golden 一致 → 放弃"像素一致"卖点，改为"视觉一致"并调整对外承诺。
- **任何阶段**：连续两个 gate 未达标 → 缩范围（砍平台或砍脚本），而不是延期。

## 7. 待拍板问题

1. **首发平台顺序**：Linux 先行（我们能自己吃狗粮，Vulkan 开发最快）还是 macOS 先行（目标客户群更愿意为"质感"付费）？
2. **是否允许两个例外**：系统字体提供者、系统图像解码（见 05-platform §5）？如果坚持 100% 自研，iOS/Android 上 HEIC/系统字体需要额外 2–3 人月。
3. **C++ API 形态**：纯 C++ 头文件 + 静态库（Qt 用户的自然选择），还是优先 C ABI + 其他语言绑定？建议前者为 1.0 目标，C ABI 同步提供。
4. **商业模型**：Apache-2.0 OR MIT 双许可（最大化采用），还是 open-core（渲染引擎开源、devtools/控件库商业）？
5. **首个真实 dogfood 应用**：选一个我们自己要用的东西（例如行情面板 / 音频工作站 / 设计工具），它的需求会决定 M1–M9 的优先级。
6. **团队**：4 人是否到位？文本轨需要有 OT/复杂脚本经验的人，这是最难招的岗位，也是最大风险。
